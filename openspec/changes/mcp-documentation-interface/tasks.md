## Delivery and dependency rules

1. The current tracker branch is `feat/mcp-documentation`. Its tracker-to-main PR is a draft integration record and remains unmerged until every child slice has been reviewed, accepted, promoted into the tracker, and verified; separately authorized ordinary-repository-policy commit and push/delivery steps are required to establish the tracker baseline, and this task artifact authorizes no branch, commit, push, PR, or merge operation.
2. PR 1 (`feat/mcp-docs-contracts`) targets `feat/mcp-documentation`; PR 2 (`feat/mcp-docs-extraction`) initially targets PR 1's branch; each later child initially targets the immediate predecessor branch in the same order shown in the slice table. Each child carries the dependency diagram with the current branch marked `📍`, its start/end state, one focused deliverable, rollback boundary, and review budget.
3. Review and promotion proceed in ascending order: review PR 1 against the tracker, accept and promote its reviewed commit into the tracker, then retarget/rebase PR 2 onto the updated tracker so its diff contains only Slice 2, review and promote PR 2, and repeat through PR 11. Do not merge a child into its predecessor before promotion, because that would turn the predecessor comparison into a combined diff and force re-review of an oversized tree.
4. If GitHub auto-deletes a child head after promotion, retain or restore that branch from the exact accepted commit before retargeting the next child; the restored head must reproduce the reviewed paths, modes, and candidate identity. Do not recreate a branch from moving main or silently discard its review evidence.
5. Only after PR 11 is accepted and all child outcomes are accumulated in `feat/mcp-documentation` may the draft tracker-to-main PR be made ready and reviewed as the final aggregate. The tracker-to-main PR is the only merge to `main`; it does not substitute for child review evidence, and no partial implementation reaches `main`.
6. Every executable slice is independently revertible and leaves the static Astro site usable when its MCP-specific behavior is removed.
7. Tests and user-facing documentation stay with the code or operational behavior they validate. Generated indexes under `dist/` are build outputs, never hand-maintained source.
8. Strict TDD is mandatory for every executable slice: after any explicitly labeled mechanical harness/dependency prerequisite, obtain meaningful RED failing behavior evidence, implement the smallest GREEN behavior, TRIANGULATE edge and negative cases, REFACTOR only while focused tests remain green, then collect check/build/focused/full evidence.
9. Source-mutating normalization happens before candidate freeze. After freeze, only check-only type checks, tests, builds, structural reads, and the native review flow may run; any mutation invalidates that candidate and requires a new normalization/freeze cycle.
10. The established browser runner remains `npx playwright test`; the focused Node runner is established as `npm run test:node` in Slice 1. Production/build gates remain `npm run check`, `npm run build`, and `npm run build:docs-mcp` where applicable.
11. HostGator plan details, TLS topology, capacity, backups, supervision, and runtime are human evidence gates. No production activation or affirmative host-specific documentation is scheduled before those gates are confirmed.
12. No task introduces WebMCP, Netlify Edge as official hosting, broad content migration, server-side LLM behavior, repository access/commands, content mutation, private content, API keys, OAuth, or undocumented HostGator features.
